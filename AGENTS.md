# Platonik repository guidance

Platonik contains a Next.js website, bounded TypeScript browser models, and a Rust shared-habitat validation prototype with a CLI and play skill. `platonik world` is the primary own-agent game loop: it carries one compact event-sourced automation world through bounded advances, admitted original-cell policy changes, and placed facility sites (industry v5 adds facilities, parts, supply/fetch logistics, and repeatable fabricator production), while `/play` recomputes and renders content-addressed world histories without mutating them. The `/lab/bridge`, `/lab/habitat`, `/lab/navigation`, `/lab/construction`, `/lab/answer`, `/lab/ark`, `/lab/ports`, and `/lab/challenges` pages display exact recorded Rust results; they must not reimplement the simulation in TypeScript. `platonik challenge` is a deterministic generated-challenge eval over three families (crossing ids 1-32, switchboard 33-64, foundry 65-96): each published id derives a train/eval case split, `eval` scores a submission's editable programs on the reserved cases, `verify` recomputes a result, and `board` ranks a directory of verified results. `platonik season` is the hosted evaluator: a committed manifest plus a secret salt in a GitHub environment scores pull-request entries on withheld per-entrant cases, and results plus the public board are committed under `season/` and `public/season/`; the `Season entry` workflow never checks out fork code and binds entrant identity to the GitHub login. A local persistent field expedition adds an append-only save, immutable program ancestry, opt-in v2 edge hazards, and frozen transfer trials. Continuous habitats preserve one immutable world's physical state and cumulative work across bounded advances and checked restoration. Navigation diagnostics preserve failed searches and compare courier programs on fixed worlds. V3 adds finite material-dependent assembly of declared bodies and ordinary child execution in that same saved world. The First Answer adds a checked local construction-to-contact ending. Ark control connects one four-bit addition to a supplied service plan and retained control of a separate payload. Port commitments add two one-shot request, custody, acknowledgment, and service obligations with finite spare stock. The full campaign, moving arks, endogenous breeding, and in-game rankings remain proposals; the hosted season board under `/lab/challenges` ranks only generated-challenge entries. Document only commands implemented by the CLI.

For every documentation surface, follow the [Hraness documentation guidelines](https://github.com/hraness/.github/blob/main/DOCUMENTATION_GUIDELINES.md): distinguish guided learning, task completion, factual reference, and explanation; keep each page or section focused on its reader's need, and link between forms. Verify prerequisites, capabilities, effects, and a complete path to the stated result. Also follow the [README guidelines](https://github.com/hraness/.github/blob/main/README_GUIDELINES.md) and [public writing style](https://github.com/hraness/.github/blob/main/STYLE.md).

## Product boundaries

- Keep the Rust engine authoritative for state and results; external agents explain and operate it.
- Keep Algal at the native CLI proposal boundary: no core/WASM dependency, no automatic provider requirement, and no accepted command without exact-view/goal receipt replay, deterministic candidate recompilation, and ordinary world admission.
- Preserve deterministic replay, explicit resource limits, independent outcome checks, and complete failure accounting.
- Distinguish illustrative output, measured performance, scientific hypotheses, and mathematical proofs.
- Keep public material self-contained. Exclude private paths, transcripts, credentials, and unlicensed copied source material.
- Changes to competitive semantics need a new version; never rewrite historical rankings silently.

## Delivery and validation

Run `bun run check` after convergence: pinned Rust 1.97.1, formatting, strict Clippy, workspace tests, exact published-artifact regeneration, content checks, browser-model tests, Next.js route generation, TypeScript, and production build. Vercel runs `check:web` because it hosts the site and static evidence only; GitHub must pass the complete aggregate gate before integration. Review desktop/mobile rendering, keyboard navigation, document anchors, overflow, and the 404 path for UI changes. For laboratory changes, also exercise editing/error recovery, deterministic replay, collection persistence/export, truth controls, budget measurement/cancellation, and signal assays/construction limits as relevant. Obtain independent review and run `git diff --check` (including the staged diff before the first commit). Browser-model tests are not Rust-engine verification; do not claim the proposed campaign has been tested.

An initial reviewed repository bootstrap may go directly to an empty main branch. Subsequent changes use a branch and pull request, with independent review and all applicable repository and GitHub checks before merging. Preserve unrelated work. The website deploys from this root to the Hraness Vercel project `platonik` at `platonik.space`. Verify the deployed domain and changed pages. No game service or package release exists yet.

The docs under `docs/` are the source for `/docs/[slug]`. The homepage is separately authored; keep its public name, capability claims, and status aligned. Public identity lives in `lib/site.ts`. No browser-side credentials or external model calls belong in this review website.

Keep the pinned Rust toolchain, locked dependencies, meaningful interpreter/replay tests, and aggregate check command synchronized. Regenerate public bridge records with `bun run bridge:record` only after reviewing the intended semantic changes. Immutable typed input and result identities must remain reproducible. The acceptance criteria in `docs/engine.md` govern the first playable claim.
